# Twelve-Factor App

Основа: [оригинальная методология](https://12factor.net/ru/).
Таблица показывает техническую поддержку факторов, а не сертификат соответствия:
часть требований обеспечивается дисциплиной релизов и инфраструктурой.

| Фактор | Реализация и границы |
| --- | --- |
| I. Кодовая база | Один Git-репозиторий; одинаковый JAR/образ для разных окружений. Изменения необходимо коммитить и версионировать. |
| II. Зависимости | Gradle Wrapper 8.14, Java 21 toolchain, зависимости в build.gradle, изолированный runtime в Docker. Образы имеют версионные теги; для строгой воспроизводимости сборочного окружения следует фиксировать digest базовых образов и сохранять собранный образ. |
| III. Конфигурация | DB_URL, DB_USER, DB_PASSWORD, PORT, LOG_LEVEL, SWAGGER_ENABLED задаются окружением. .env исключён из Git. Демонстрационные настройки существуют только в локальной задаче и примере. |
| IV. Сторонние службы | PostgreSQL подключается по JDBC URL. Можно сменить сервер без пересборки. Compose предоставляет локальный PostgreSQL; при внешней БД его поднимать не требуется. |
| V. Сборка / релиз / выполнение | Gradle создаёт JAR, Docker упаковывает его. Релиз связывает неизменяемый тег/образ с конфигурацией и миграциями. Runtime не собирает исходники. CI сохраняет JAR под SHA коммита и проверяет сборку образа; публикацию/деплой нужно подключить к выбранной платформе. |
| VI. Процессы | Бизнес-данные сохраняются в PostgreSQL; приложение не использует локальный диск или память как постоянное хранилище. Контейнеры web не имеют томов с данными. |
| VII. Привязка портов | Встроенный Tomcat, порт задаётся PORT. Для JAR по умолчанию 8080; Compose назначает каждой реплике собственный порт хоста. |
| VIII. Параллелизм | Можно запускать несколько web-процессов с общей БД. Пример ниже. Для единого публичного адреса требуется балансировщик на стороне инфраструктуры; конкурентность операций предметной области требует отдельных нагрузочных тестов. |
| IX. Утилизируемость | Java запускается напрямую как PID 1; SIGTERM вызывает graceful shutdown, ожидание 20 секунд, Compose даёт 30 секунд. /actuator/health/readiness включает доступность БД. Миграции вынесены из обычного старта web. |
| X. Паритет окружений | Java 21, PostgreSQL 16 и одни миграции в контейнерном запуске и тестах; CI запускает unit/HTTP и integrationTest. Одинаковый образ можно продвигать между окружениями. |
| XI. Журналирование | Стандартные логи Spring/SLF4J идут в консоль; файловый журнал не настраивается. Сбор, хранение и ротацию обеспечивает Docker или платформа. |
| XII. Администрирование | java -jar dealership.jar --migrate запускает миграции тем же артефактом и с той же конфигурацией, без HTTP-сервера, затем завершается. При ошибке процесс завершается с ненулевым кодом. |

## Сборка

Нужны JDK 21, Docker и Compose. Gradle 8.14 нельзя запускать на системной Java 26:
задайте JAVA_HOME на установленную Java 21 либо выберите Gradle JVM 21 в IDE.

```sh
./gradlew check bootJar
docker build -f docker/Dockerfile -t dealership:local .
```

`check` включает `test` и `integrationTest`; PostgreSQL для тестов изолирован через Testcontainers.
Для релиза вместо `local` используйте уникальный тег, например SHA коммита, и не перезаписывайте его.
Один образ продвигайте между средами без пересборки. CI пока не публикует образ в registry.

## Локальный контейнерный релиз и масштабирование

```sh
cp .env.example .env
docker compose up -d --scale web=2 --wait
docker compose port --index=1 web 8080
docker compose port --index=2 web 8080
```

Compose сначала ждёт БД, затем выполняет `migrate`, и только после его успешного
завершения запускает web. Swagger доступен по адресу `http://127.0.0.1:<выданный порт>/swagger-ui.html`.
Этот Compose использует отдельный том, не базу старой команды `bootRunLocal`.
`.env` автоматически читает Compose, но не `java -jar` и не Gradle.

```sh
docker compose logs -f web
docker compose stop web
docker compose down
```

`down` без `-v` сохраняет данные. В production назначьте собственные credentials,
не включайте `DB_CONTEXTS=demo`, отключите Swagger, если он не нужен.
`demo` добавляет учебные записи, включая пользователей с демонстрационными паролями.
Изменение контекста не удаляет данные, которые были добавлены ранее.

## Отдельный сервер БД и запуск JAR

Экспортируйте `DB_URL`, `DB_USER`, `DB_PASSWORD` через окружение процесса или менеджер секретов.
Они обязательны, секретов по умолчанию в приложении нет. Перед стартом новой версии:

```sh
java -jar build/libs/dealership.jar --migrate
PORT=8080 SWAGGER_ENABLED=true java -jar build/libs/dealership.jar
```

Обычный сервер не выполняет миграции (`MIGRATIONS_ENABLED=false`). Для локальной
разработки `bootRunLocal` сознательно совмещает старт БД, миграции и запуск.
Для повторной административной задачи с текущим Compose-релизом:

```sh
docker compose run --rm migrate
```

При замене версии образа выполните миграцию нового релиза перед обновлением web:

```sh
docker compose run --rm migrate
docker compose up -d --no-deps --scale web=2 web
```

Перед этим задайте новый APP_IMAGE в конфигурации релиза. Изменение схемы должно
оставаться совместимым со старой версией на время обновления. Откат приложения
не откатывает автоматически схему и данные БД.

## Проверка окружения

- `/actuator/health/liveness` — состояние процесса.
- `/actuator/health/readiness` — готовность обслуживать запросы, включая соединение с БД.
- `docker compose ps -a` — migrate должен завершиться с кодом 0, web быть healthy.
- `docker compose stop web` — в логах должно появиться завершение graceful shutdown.

Здесь не развёрнуты внешний балансировщик, registry, централизованный сбор логов
и production-инфраструктура. Их настройки зависят от выбранной площадки.
